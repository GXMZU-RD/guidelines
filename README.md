# 协作规范

三条主线：**分支怎么走、PR 怎么收、权限怎么给**。规范之外不挑刺——规范了就行。

## 一、分支

- 长期分支只有两条：`main` 是发布线，`develop` 是开发线；其余分支合并即删。
- `main` 只接受来自 `develop` 的 PR；日常一律向 `develop` 提。
- 分支命名：`feature/xxx`、`bugfix/xxx`、`docs/xxx`。

## 二、PR 红线

打回只写编号，不写理由。

| 编号 | 红线 |
| :--- | :--- |
| P0 | diff 里出现密钥、令牌、口令、个人数据——出现即打回，并立即更换 |
| P1 | 强制推送覆盖历史、删主干或他人分支、绕过保护直改主干 |
| P2 | 一个 PR 混了不相干改动，或提交构建产物、模型权重、日志、依赖目录 |
| P3 | 目标分支不是 `develop`，或未 rebase 最新 `develop`、存在冲突 |
| P4 | 标题不是 `feat:` / `fix:` 开头 |
| P5 | 描述缺「目的 / 改动 / 测试」三段，或自查清单未逐条勾选 |
| P6 | 仓库配了 CI 但本 PR 未通过 |

## 三、评审

- 合并前需 **1 名**评审人批准（起步阶段先 1 人，稳定后升到 2 人）；作者本人不能批准自己的 PR。
- 评审只依据上面的红线表，风格偏好不构成拒绝理由。

## 四、权限

组织默认对所有仓库零权限：**进哪个组才看得见哪个仓**。

| 组 | 范围 |
| :--- | :--- |
| `governance` | 组织设置、建仓删仓、成员与评审指派 |
| `reviewers` | 全部项目仓的评审与合并 |
| `members` | 公开仓只读；项目仓需单独授权 |

## 五、仓库验收

README 五段：项目简介、硬件与设备依赖、环境配置、使用方法、维护团队（写组名不写个人账号）。
LICENSE 默认 MIT；依赖清单随代码提交；CODEOWNERS 用组名，换届只改组成员。
